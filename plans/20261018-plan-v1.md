- **Date:** 2026-10-18
- **Branch:** `v1-exec-plan`

- **Status:** Reviewed & Amended (Incorporating Live Google Sheet Data Patterns)

## 1. Overview and Motivations

### 1.1 Problem Statement & Real-World Workflow
Users currently track daily nutritional intake across spreadsheets using a 3-row-per-date layout:
- **Row 1 (Food Items):** Text descriptions of individual items or multi-ingredient meals (e.g., `"40g Oats w 120g soy milk, 170g yogurt"`, `"Just Salad earth bowl w chicken (dressing 150cal)"`, `"225g baked sweet potato; 110g baked carrots, 115g chk breast; frozens"`).
- **Row 2 (Calories):** Caloric intake per item (often fractional based on weight, e.g., `213.75`, `597.975`).
- **Row 3 (Protein):** Protein in grams per item (often fractional, e.g., `11.25`, `72.159`). Notably, items often have empty or 0 protein values (e.g., drinks, fruits, snacks).
- **Totals Column:** Running sum of daily calories and protein.

#### Limitations of Current Process:
1. **Manual Entry Friction & Repetition:** Routine meals (e.g., the oats recipe logged on 10/14, 10/16, 10/18, 10/19, or "IP congee" logged multiple times a week) must be manually re-typed and re-calculated.
2. **Missing Granular Analytics:** No immediate visualization showing nutritional consistency across days or macro trends over time.
3. **Multi-Item / Non-Contiguous Gaps:** Dates can have variable entry counts (from 4 items to 7+ items), non-continuous date logs (e.g., jump from 10/7 to 10/12), and zero/null protein values that must not break aggregate calculations.

### 1.2 Objective
Build a modern, robust, responsive web application backed by PostgreSQL (Supabase) and FastAPI with a React + TypeScript frontend that:
1. Enables structured logging of individual meal/food items per day with calorie (kcal) and protein (grams) tracking.
2. Accommodates real-world logging behaviors: optional/null protein fields (defaulting to 0 in calculations), fractional macro numbers, and multi-ingredient descriptions.
3. Computes automated daily summaries and running totals.
4. Renders an interactive, overlaid dual-axis graph (X-axis: Date, Left Y-axis: Calories [kcal], Right Y-axis: Protein [g]).
5. Houses an extensible data schema supporting reusable food item templates for fast single-click logging of frequent meals.
6. Enforces tenant/user isolation in the database schema from v1 so future multi-user support requires zero schema redesign.

## 2. Implementation Steps

### Step 2.1: Relational Schema & Migrations (PostgreSQL via Supabase)
Define normalized, performant relational tables in Supabase:

1. **`users` Table (or Supabase `auth.users`)**:
   - `id`: `UUID PRIMARY KEY DEFAULT gen_random_uuid()`
   - `email`: `TEXT UNIQUE NOT NULL`
   - `created_at`: `TIMESTAMPTZ DEFAULT now()`

2. **`food_templates` Table** (Template catalog for rapid re-entry):
   - `id`: `UUID PRIMARY KEY DEFAULT gen_random_uuid()`
   - `user_id`: `UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE`
   - `name`: `TEXT NOT NULL` (e.g., "40g Oats w 120g soy milk, 170g yogurt")
   - `default_calories`: `NUMERIC(8, 3) NOT NULL` (accommodates fractional scale calculations like `597.975`)
   - `default_protein`: `NUMERIC(7, 3) NOT NULL DEFAULT 0.0`
   - `category`: `TEXT NULL` (e.g., "Breakfast", "Snack", "Dinner")
   - `created_at`: `TIMESTAMPTZ DEFAULT now()`
   - *Index:* `CREATE INDEX idx_food_templates_user ON food_templates(user_id);`

3. **`daily_logs` Table**:
   - `id`: `UUID PRIMARY KEY DEFAULT gen_random_uuid()`
   - `user_id`: `UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE`
   - `date`: `DATE NOT NULL`
   - `notes`: `TEXT NULL`
   - `created_at`: `TIMESTAMPTZ DEFAULT now()`
   - *Constraint:* `UNIQUE(user_id, date)`
   - *Index:* `CREATE INDEX idx_daily_logs_user_date ON daily_logs(user_id, date);`

4. **`meal_entries` Table**:
   - `id`: `UUID PRIMARY KEY DEFAULT gen_random_uuid()`
   - `daily_log_id`: `UUID NOT NULL REFERENCES daily_logs(id) ON DELETE CASCADE`
   - `template_id`: `UUID NULL REFERENCES food_templates(id) ON DELETE SET NULL`
   - `name`: `TEXT NOT NULL`
   - `calories`: `NUMERIC(8, 3) NOT NULL`
   - `protein`: `NUMERIC(7, 3) NOT NULL DEFAULT 0.0` (allows nulls to coerce safely to 0)
   - `sort_order`: `INT NOT NULL DEFAULT 0`
   - `created_at`: `TIMESTAMPTZ DEFAULT now()`
   - *Index:* `CREATE INDEX idx_meal_entries_log_id ON meal_entries(daily_log_id);`

### Step 2.2: Backend API Layer (FastAPI & Pydantic)
Implement cleanly structured routes and business logic in `backend/app/`:

1. **Schemas (`app/schemas.py`)**:
   - `MealEntryCreate`: `name: str`, `calories: float`, `protein: Optional[float] = 0.0`, `template_id: Optional[UUID] = None`.
   - `DailyLogResponse`: `id: UUID`, `date: str`, `entries: List[MealEntryResponse]`, `total_calories: float`, `total_protein: float`.
   - `AnalyticsDayPoint`: `date: str`, `total_calories: float`, `total_protein: float`, `entry_count: int`.
   - `FoodTemplateCreate` & `FoodTemplateResponse`.

2. **Routes (`app/api/`)**:
   - `GET /api/logs?start_date=YYYY-MM-DD&end_date=YYYY-MM-DD`: Returns logs within window, with individual entries and calculated totals.
   - `GET /api/logs/{date}`: Returns full details for a single day.
   - `POST /api/logs/{date}/entries`: Append a meal entry. If `daily_log` doesn't exist for that date, atomically create it.
   - `PUT /api/entries/{entry_id}`: Edit meal entry name or nutritional values.
   - `DELETE /api/entries/{entry_id}`: Remove an entry and cascade update totals.
   - `GET /api/analytics/timeseries?start_date=YYYY-MM-DD&end_date=YYYY-MM-DD`: Optimized aggregation returning daily totals for charting. Missing dates in the range can optionally be zero-filled or returned as sparse points.
   - `GET /api/templates`: Fetch user's saved templates.
   - `POST /api/templates`: Create new template from scratch or directly from a logged entry.

### Step 2.3: Frontend UI Components (React + TypeScript)
Modular layout in `frontend/src/`:

1. **`DayLogView`**:
   - Date picker with "Previous Day" and "Next Day" controls.
   - Summary banner: **Total Calories: 1,840 kcal** | **Total Protein: 132g**.
   - Entry list with clear visual hierarchy:
     - Name (with badge if derived from template).
     - Calories (kcal).
     - Protein (g) — cleanly handles items with 0g or no protein (e.g. grapes, drinks).
     - Inline edit / delete actions.
   - Quick "Add Item" bar:
     - Quick Template Selector dropdown.
     - Inputs for Name, Calories, Protein.
     - Option to check: *"Save as reusable template"*.

2. **`DualAxisMacroChart` (Recharts)**:
   - Synchronized line / area chart.
   - **X-Axis**: Dates (`YYYY-MM-DD`).
   - **Left Y-Axis (Y1)**: Total Calories (kcal), range scaled dynamically (e.g. 1000 - 2500 kcal).
   - **Right Y-Axis (Y2)**: Total Protein (grams), range scaled dynamically (e.g. 50 - 200 g).
   - Differentiated stroke colors and fill gradients (e.g., Warm Amber for Calories, Ocean Blue / Orange for Protein).
   - Synchronized hover tooltip displaying date, items count, total kcal, and total protein.
   - Range selection pills: `7D`, `14D`, `30D`, `All`.

3. **`TemplateDrawer`**:
   - Drawer / modal to manage saved favorite foods, edit their default macros, or delete outdated recipes.

## 5. Discoveries, Learnings, and Rationale for Design Decisions

### 5.1 Real Data Insights from Google Sheets Analysis
Direct inspection of the user's Google Sheet (`10/6/2026` through `10/19/2026`) revealed several key domain realities:
- **High-Precision Decimals:** Entries like `213.75` kcal (10/7), `597.975` kcal (10/12), and `72.159`g protein (10/12) reflect kitchen scale measurements (e.g. batch cooking calculations like *"IP congee 770g + kimchi 56g"*). Standard integer storage would discard significant macro tracking data.
- **Sparse Protein Logging:** Many snacks, coffees, and drinks (e.g., banana bread, espresso tonic, dried mangos, sweet potato) have calories entered but blank protein cells. The system must treat missing protein as `0.0` rather than required non-null inputs.
- **Identical Repeated Recipes:** The item `"40g Oats w 120g soy milk, 170g yogurt"` was entered identically across 4 separate days (10/14, 10/16, 10/18, 10/19) with `315` kcal and `32`g protein. This strongly validates the user's intuition for food item templates.
- **Date Gaps:** The sheet skips days (e.g., 10/8 through 10/11 are absent). The timeseries visualization must handle missing dates gracefully (providing a contiguous timeline option or discrete point connects).

### 5.2 Template Snapshot Pattern
- **Decision:** When an entry is logged using a template, the `name`, `calories`, and `protein` values are copied directly into `meal_entries`, with a nullable `template_id` reference.
- **Rationale:** If the user alters a template recipe in the future (e.g. switches to almond milk), historical logs from previous weeks must remain immutable.

### 5.3 Dual-Axis Charting Justification
- **Scale Disparity:** Daily calories range between `1,400` and `2,225` kcal, while daily protein ranges between `100` and `153` grams.
- **Decision:** Overlay two line series with independent Y-axes (Left: Kcal [0–2500], Right: Grams [0–200]). This ensures fluctuations in protein intake are as visually pronounced and actionable as calorie changes.

### 5.4 Forward-Compatible Multi-User Architecture
- **Decision:** Every table (`daily_logs`, `meal_entries`, `food_templates`) includes a `user_id` column indexed for fast lookups.
- **Rationale:** In v1, queries will scope to a default user context. When authentication and multi-user views are enabled in v2, no schema migrations or destructive table changes will be required.
